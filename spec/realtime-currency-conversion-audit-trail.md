**Title:** Real-Time Currency Conversion & Audit Trail

**Business Idea:** Treasury operations teams at our enterprise customers
currently convert currency using manual lookups against a third-party
portal — slow, and it leaves no record for compliance. We need instant,
self-serve conversion inside our own app, and because these are regulated
transactions, every conversion must be reconstructable for an auditor on
demand, not pieced together afterward from emails or spreadsheets.

**Persona:** Treasury operations analysts at enterprise customers, who
process multiple cross-border settlements a day and are personally
accountable if a conversion can't be justified during an audit.

**User Need:** See a trustworthy converted amount the moment I enter it
— and be able to pull up any past conversion, with its rate and timestamp,
the moment an auditor asks for it.

**Known Constraints:**
- Frontend must read `VITE_API_URL` dynamically at container runtime using
  a generic entrypoint script placeholder replacement; replace the placeholder token
  `__VITE_API_URL__` inside the built `index.html` (or equivalent) with the runtime
  `VITE_API_URL` value.
- Backend must read database configurations exclusively from runtime
  environment variables.
- Backend must query external currency conversion data exclusively using a base URL from an environment variable (`CURRENCY_API_BASE_URL`), defaulting to an unauthenticated open-source endpoint like Frankfurter (`https://frankfurter.dev`).
- The application must not hardcode third-party API response schemas; utilize flexible JSON property mapping or an abstraction layer to isolate internal compliance tracking from external JSON structure changes (such as `rates` vs `conversion_rates`).
- The audit trail record must capture the exact execution timestamp generated by your backend server alongside any date or sequence markers returned by the external provider, ensuring complete sub-second audit reconstruction even if the provider only exposes a calendar date.
- External HTTP calls must handle failures gracefully with fallback values or clear domain exceptions rather than bubbling up raw network or serialization errors.
- CI/CD pipeline must inject placeholders safely at deployment time without
  exposing sensitive data in container layers.
- Restricted to specific stack versions: React (Vite/Node 24.*) and C#
  (**backend must target `net10.0` for build/test; CI must use `dotnet-version: 10.0.x`**).
- Must adhere to a strict folder layout (`src/frontend` and `src/backend`).
- A .NET solution file must always be generated at `src/backend/OuterloopLabApi.sln` via `dotnet new sln` + `dotnet sln add`, with the backend project added to it, and CI/build/test commands must invoke this `.sln` rather than the `.csproj` directly.
- Deploy as a single Azure Container App using the sidecar pattern to host
  both frontend and backend.
- Authenticate to Cosmos DB exclusively using token-based authentication via the pre-assigned User-Assigned Managed Identity, instantiated using `DefaultAzureCredential` configured with the specific `ManagedIdentityClientId`. Absolutely zero connection strings, master keys, or account keys are permitted in code, configurations, or logs.
- Utilize `Microsoft.Azure.Cosmos` and `Azure.Identity` packages for
  secure, token-based database interactions, including data-plane CRUD operations like adding and deleting items.
- Include `Azure.ResourceManager` and `Azure.ResourceManager.CosmosDB` packages to programmatically provision the Cosmos DB database and container via the control plane inside the application startup lifecycle (`Program.cs`) before the web application runs, utilizing the same token-based Managed Identity credentials for authentication.
  - ARM provisioning is best-effort; Managed Identity RBAC for ARM may differ from data-plane RBAC.
  - CRUD (and data-plane creation if needed) must be done via the Cosmos SDK (data-plane) using token-based Managed Identity credentials; access keys must not be used.
  - After ARM attempt, startup must run token-authenticated data-plane `CreateDatabaseIfNotExistsAsync` and `CreateContainerIfNotExistsAsync` and only proceed if the database/container are available (either already exist or were created). If token-authenticated data-plane create-if-not-exists fails, startup must fail.
- Map and bind all configuration values, including `AZURE_MANAGED_IDENTITY_CLIENT_ID`, endpoint URLs, and resource names, directly from the environment variables **using the exact keys** defined in `docs\CONTAINER_ENVIRONMENT_VARIABLES.md` without using local settings configuration files as fallbacks.

**Current Context:** Assuming a standard Vite + ASP.NET implementation inside the required folders, the concrete feature touchpoints should be `src/backend/OuterloopLabApi.sln`, `src/backend/Program.cs`, `src/backend/Controllers/ConversionsController.cs` (or `src/backend/Endpoints/ConversionsEndpoints.cs` if the app already uses minimal APIs), `src/backend/Services/CurrencyRateProvider.cs`, `src/backend/Services/ConversionService.cs`, `src/backend/Repositories/ConversionAuditRepository.cs`, `src/backend/Models/ConversionRequest.cs`, `src/backend/Models/ConversionResponse.cs`, `src/backend/Models/ConversionAuditRecord.cs`, `src/frontend/index.html`, `src/frontend/src/main.tsx`, `src/frontend/src/App.tsx`, and `src/frontend/src/api/conversions.ts`; if any of these files do not exist yet, create them at these exact paths rather than placing feature code outside `src/backend` or `src/frontend`.

**In Scope:**
- Add a backend API endpoint that accepts a conversion request with source currency, target currency, and amount, calls the external rate provider, computes the converted amount, and returns the persisted audit identifier plus all audit-relevant fields needed by the UI.
- Add a backend API endpoint that retrieves a previously stored conversion audit record by its identifier so an auditor or analyst can reconstruct the original conversion later.
- Persist one immutable Cosmos DB audit record per successful conversion, including request values, normalized provider rate data, provider date/sequence metadata when present, and the exact backend execution timestamp with sub-second precision.
- Add a backend abstraction layer that normalizes provider responses into an internal rate model so the compliance/audit flow is insulated from upstream JSON schema differences.
- Add a frontend workflow in `src/frontend` that lets the user enter amount/from/to currencies, submit the request, immediately view the converted result, and then retrieve a past conversion by audit identifier.
- Ensure the frontend reads the API base URL at runtime through the existing placeholder replacement pattern so the new conversion and lookup calls do not assume a build-time API URL.

**Out of Scope:**
- User authentication, authorization, or role-based audit access rules.
- Batch conversion uploads, CSV import/export, or bulk settlement processing.
- Historical charting, trend analysis, dashboards, or reporting beyond direct conversion lookup.
- Manual editing or deletion of audit records after they are created.
- Custom treasury pricing logic such as spreads, fees, commissions, or negotiated customer-specific FX rates.
- Multi-provider routing or advanced resilience patterns beyond the single configured provider plus graceful failure handling.

**Feature Constraints:**
- Use `IHttpClientFactory` for the outbound currency-rate client so HTTP behavior is centralized and testable.
- Normalize upstream JSON into an internal model such as `baseCurrency`, `targetCurrency`, `rate`, `providerDate`, and optional provider sequence/reference fields; support both map-style payloads (for example `rates.EUR`) and alternate property names (for example `conversion_rates.EUR`) without leaking those shapes into controllers or persistence code.
- Validate request currency codes as exactly three uppercase alphabetic characters before calling the provider; reject invalid requests with `400 Bad Request` and a `ProblemDetails` payload.
- Use `decimal` for amount and rate calculations; store the original amount, normalized rate, and converted amount explicitly in the audit record rather than recomputing from display text later.
- Treat the audit record as append-only: on success write exactly one record, and on upstream/provider failure do not persist a partial or placeholder record.
- Return `ProblemDetails` for provider or normalization failures with HTTP `503`, using a domain message such as `Currency rate provider unavailable`, instead of surfacing raw exceptions.
- Format backend execution timestamps in UTC ISO 8601 form with fractional seconds (for example `2026-01-15T14:03:27.481Z`) so audit reconstruction is precise and consistent.

**Expected Outcome:** A user can submit a request such as `POST /api/conversions` with `{ "amount": 100.00, "fromCurrency": "USD", "toCurrency": "EUR" }`, and if the configured provider yields a normalized rate of `0.92` with provider date `2026-01-15`, the API responds with HTTP `200` and a body containing a non-empty audit identifier plus values equivalent to `{ "amount": 100.00, "fromCurrency": "USD", "toCurrency": "EUR", "rate": 0.92, "convertedAmount": 92.0000, "providerDate": "2026-01-15", "executedAtUtc": "2026-01-15T14:03:27.481Z" }`; the same values are persisted in Cosmos DB and later returned by `GET /api/conversions/{auditId}`. The frontend renders the converted amount, rate, provider date, execution timestamp, and audit identifier immediately after submission, and a user can paste that audit identifier into the lookup flow to retrieve the same record. If the provider call fails, times out, or returns a payload that cannot be normalized into a target-currency rate, the API returns HTTP `503` with `ProblemDetails`, no partial audit record is stored, and the frontend shows a clear failure state instead of stale or guessed conversion data.
